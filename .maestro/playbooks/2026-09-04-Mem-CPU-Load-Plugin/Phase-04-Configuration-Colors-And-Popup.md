# Phase 04: Configuration, Colors, Watch Mode, and Status Popup

This phase makes the plugin comfortable to live with. Users get a `config.toml` under the herdr-managed plugin config directory for interval, thresholds, graph style, widths, and display modes; thresholds gain hysteresis so level tokens do not flicker; the daemon becomes a singleton across herdr live handoffs; one-line mode gets the original tmux 256-color markup back (true drop-in replacement) plus ANSI colors for plain terminals; and a `--watch` mode powers a herdr popup pane that shows a live status line on demand. The README grows into complete documentation.

## Tasks

- [ ] Add a configuration file layer in `src/config.rs` (add `toml = "0.8"` to `Cargo.toml`; `serde` is already present):
  - `#[derive(Deserialize, Serialize, Default)] pub struct FileConfig` mirroring every daemon and rendering option: `interval_secs`, `ttl_ms`, `source`, `graph_style`, `graph_lines`, `mem_graph_lines` (optional override for the memory bar width), `mem_mode`, `cpu_mode`, `averages_count`, `history`, `verbose`, and a nested `[thresholds]` table with `cpu_warn`, `cpu_hot`, `mem_warn`, `mem_hot`, `load_warn`, `load_hot`. Every field is `Option<_>` so the file may set only what it wants; use `#[serde(deny_unknown_fields)]` so typos fail loudly with the file path and line in the error.
  - Resolution order (highest wins): explicit CLI flags, then `--config <PATH>`, then `$HERDR_PLUGIN_CONFIG_DIR/config.toml`, then built-in defaults. Implement this by making the clap struct fields `Option<_>` and merging in `pub fn resolve(cli: &Cli, file: Option<FileConfig>) -> Settings` where `Settings` is the fully-populated struct that `daemon.rs` and one-line mode consume. Search the existing code for the `DaemonOptions`, `TokenOptions`, and `RenderOptions` structs and construct them from `Settings` instead of duplicating fields.
  - Add `--print-config` (prints the effective `Settings` as TOML to stdout and exits) and `--write-default-config` (writes a fully commented default `config.toml` into `HERDR_PLUGIN_CONFIG_DIR`, or `--config` path if given, refusing to overwrite an existing file unless `--force`). The commented template lives in `src/config/default_config.toml` and is embedded with `include_str!`.
  - A missing config file is not an error; a malformed one is logged and reported to stderr, and the daemon continues with defaults so a typo cannot silently kill the sidebar.

- [ ] Add hysteresis and thread the memory bar width through rendering:
  - In `src/tokens.rs`, replace the stateless `classify` call with `pub struct LevelTracker { cpu: Level, mem: Level, load: Level }` and `fn next(current: Level, value: f64, warn: f64, hot: f64, margin: f64) -> Level` that escalates when `value ≥ threshold` and only de-escalates when `value < threshold - margin` (margin 5 percentage points for cpu/mem, 0.1 for load-per-core). `build_tokens` takes `&mut LevelTracker`; keep the pure classifier for the first sample.
  - Use `mem_graph_lines` (defaulting to `graph_lines`) for the `mem_status` and `mem_*` level tokens.

- [ ] Make the daemon a singleton in `src/daemon/lock.rs` so a live handoff (which re-runs `[[startup]]` hooks) or a manual second start cannot double-report:
  - Acquire an OS advisory lock on `<HERDR_PLUGIN_STATE_DIR or std::env::temp_dir()>/herdr-mem-cpu-load.lock`: `libc::flock(fd, LOCK_EX | LOCK_NB)` on Unix and `LockFileEx` with `LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY` on Windows (add the `Win32_Storage_FileSystem` feature to `windows-sys`). Keep the `File` open for the daemon's lifetime; the OS releases the lock when the process exits or is killed, so no stale-pid logic is needed.
  - If the lock is held, log `another herdr-mem-cpu-load daemon is already running` and exit 0 (not an error, so the herdr plugin log stays clean).
  - Write the pid into the lock file after acquiring it for human debugging.
  - Unit test on Unix: acquiring the lock twice in one process from two `File` handles fails the second time (spawn a child process via `std::process::Command` running the test binary with an env-var-guarded helper if same-process `flock` semantics make the two-handle test unreliable).
